# Autopsy: Why "Hash the 200-Word Query Window; Extend TTL to 90s" Keeps Recurring

## What This Document Is

This is a root-cause analysis of why a specific incorrect fix — "hash the last-200-word
query window instead of last-500 chars; extend TTL to 90 seconds" — has been
independently proposed by multiple analysis passes, encoded into authoritative
project documents, and continues to appear in recommended project timelines.

The fix does not work. `NEW_CACHE_ANALYSIS.md` proves this in detail.
This document explains the institutional failure that keeps reproducing it.

---

## The Propagation Chain

The fix did not originate from a human decision. It was generated by an LLM code review,
written into documentation with the authority of a "completed investigation," and then
read back as ground truth by every subsequent LLM session.

```
LLM code review pass
        ↓
backend/CACHE_ANALYSIS_REPORT.md  ← "investigation already complete"
        ↓
backend/cache.md                  ← "implement fixes in priority order below"
        ↓
technical.md (project roadmap)    ← "Fix the RAG cache key [...] extend TTL to 90 seconds"
        ↓
LLM_CONTEXT/TherAssist-AgentHandoff.md  ← read by every incoming agent
        ↓
Next LLM session → proposes the same fix
```

Once the fix entered `backend/cache.md` — a document whose opening line reads
*"Prerequisite reading: `backend/CACHE_ANALYSIS_REPORT.md` (investigation already complete —
do not re-derive)"* — no subsequent agent would re-examine it. The instruction not to
re-derive is the exact mechanism by which the error became permanent.

---

## The Original Reasoning Error

The error first appears in `backend/CACHE_ANALYSIS_REPORT.md` at the
"Secondary design flaw" section:

> "200 words × ~6 chars/word ≈ 1,200 chars ≈ 86 seconds of speech. Two consecutive
> calls where the 200-word query would retrieve **nearly identical passages** (stable
> clinical topic) may still produce different 500-char hashes and trigger a redundant
> fetch."

This conflates two different claims:

| Claim | Type | True? |
|---|---|---|
| Two consecutive 200-word windows retrieve semantically similar passages | Semantic / about retrieval quality | Possibly true for stable topics |
| Two consecutive 200-word windows produce the same hash | Deterministic / about string equality | **Always false** — 8 new words are appended at the tail on every trigger |

The fix resolves the first claim (aligning hash input with query input is internally
consistent) while leaving the second claim completely unaddressed. Because the hash
is computed over the string value of the window — not a semantic digest of it — adding
8 new words to the tail of the 200-word window produces a different hash regardless of
whether those words shift the clinical topic.

The document recognizes something is wrong with the 500-char window ("the cache key
shifts faster than the underlying query changes") but misidentifies the mechanism.
The problem is not that the 500-char window is narrower than the 200-word window.
The problem is that **any window whose tail changes on each trigger produces a
different hash on each trigger.** Making the window wider in word-count terms does
not change this.

## The Test Spec Proves the Fix Is Wrong On Its Own Terms

`backend/cache.md` includes a proposed unit test:

```
test_cache_key_uses_query_window:
  - Build a transcript of 250 words.
  - Append a single short utterance (< 10 words).
  - Assert new method: hash unchanged (200-word window didn't shift significantly).
  - Assert old method: hash changed (500-char window shifted).
  → Documents the fix is correct.
```

This test would **fail** with the proposed fix applied, for the following reason:

- Start: 250-word transcript. Last 200 words = words 51–250.
- After appending 8 words: 258-word transcript. Last 200 words = words 59–258.
- The two windows differ in 16 entries (8 dropped from the front, 8 added at the back).
  The string value is different. The hash is different.

The test asserts "hash unchanged" but the hash will have changed. The test spec was
written under the same false premise as the fix: that a bigger window is a more stable
window. This would have been caught the moment the test was actually run.

The trigger threshold is 8 words minimum. The test condition is "< 10 words." These
ranges overlap. The test is testing the scenario that actually triggers analysis and
asserting it produces a cache hit — but it would not.

## Why Each LLM Session Reproduces the Same Error

### 1. The comment at line 498 primes the "extend TTL" recommendation

```python
# The corpus is static clinical documents — passages stay valid for minutes.
```

Every analysis session reads this comment. "Valid for minutes" creates an immediate anchor:
the TTL is too short. The fix "extend to 90 seconds" is the direct response to this
anchor. This is correct reasoning from a false premise — the TTL is not the binding
constraint, but the comment does not say that.

### 2. The docstring obscures which half of the condition is failing

```python
def prefetch_rag_context(session_context: dict, transcript_text: str) -> str:
    """Uses a cache keyed by session_type + transcript hash to avoid redundant queries."""
```

"Keyed by session_type + transcript hash" sounds like a reasonable compound key.
It does not surface that the hash is computed over the always-changing tail of a
growing string. A reader has to trace the calling convention backward to the
frontend trigger to understand that `transcript_text` grows on every call.
Most analysis passes do not go that far.

### 3. The fix is locally coherent within the function

Viewed in isolation, `prefetch_rag_context` contains two computations:

```python
transcript_hash = str(hash(transcript_text[-500:] ...))  # line 569
...
query_text = " ".join(words[-200:]) ...                  # line 587
```

These are inconsistent: the hash uses a different window than the query.
Aligning them — hashing `query_text` — is a genuine internal consistency improvement.
It is also completely ineffective at fixing cache misses. But it *looks* like a fix
because it removes a discrepancy.

LLMs pattern-match well on internal consistency. "The hash should match the query"
is the kind of localized reasoning that reads as correct without requiring cross-layer
understanding of when and why `transcript_text` changes between calls.

### 4. The authoritative documents suppress re-investigation

`backend/cache.md` opens with: *"investigation already complete — do not re-derive."*

This instruction is intended to save time. Its effect is to prevent any subsequent
agent from questioning the premises of the fix. An agent that reads this document
treats the analysis as settled and moves directly to implementation. The error is
load-bearing in a document explicitly designed to suppress its discovery.

`LLM_CONTEXT/TherAssist-AgentHandoff.md` lists the finding directly:

> "The TTL never becomes the binding constraint because the hash always fails first."

This is the correct diagnosis. The same document then proposes Option C3:

> "Change the hash input from `transcript[-500:]` to `transcript[-5000:]`"

This is the same error with a larger number. The document correctly identifies the
mechanism of failure (hash fails first) and immediately proposes a fix that does not
address it (make the hash window bigger). A reader who trusts the handoff document
inherits both the correct diagnosis and the wrong conclusion simultaneously.

### 5. The fix produces hits in test conditions, not production conditions

In demo mode, test mode, or slow-speech scenarios, consecutive analysis calls can arrive
with fewer than 8 new words (the time-based fallback fires at 20s; the word accumulator
resets after analysis; interim entries are filtered). In these conditions, the last
200 words may actually be stable between two consecutive calls, producing a cache hit.

This means the fix passes casual smoke-testing. A developer running the app manually
and speaking slowly or pausing mid-sentence will observe cache hits and conclude the
fix works. The failure mode only manifests at clinical conversational pace (~130 wpm),
exactly the condition under which the system is deployed.

## What Needs to Happen

### 1. Correct `backend/CACHE_ANALYSIS_REPORT.md`

The "Secondary design flaw" section contains the original error. It must be corrected
or the document will continue to generate wrong conclusions. The correct framing is:

> The cache key uses `hash(transcript_text[-500:])`. The query uses the last 200 words.
> Aligning these does not fix cache misses. Both windows include the tail of a growing
> string. Any window computed over the tail changes on every trigger.
> The hash check must be either removed or computed over a stable region of the transcript.

### 2. Correct `backend/cache.md`

Task 1 in the session bootstrap implements the wrong fix. The test spec in §4 would
fail if run. The "Definition of Done" would pass even if cache hits never occurred,
because it only checks that `context_cache_hit` appears in the response — not that
it is ever `True`.

The document should either be replaced with a correct implementation plan (see
`NEW_CACHE_ANALYSIS.md` §What Would Actually Resolve the Issue) or marked as
superseded.

### 3. Correct `technical.md:149`

The roadmap item reads:

> "Fix the RAG cache key (hash the last-200-word query window, not the last-500 characters
> of raw transcript text; extend TTL to 90 seconds)"

This item will be scheduled, implemented, and marked done without producing any
observable improvement in cache hit rate. It should be replaced with a correct
description, e.g.:

> "Fix the RAG prefetch cache: remove transcript hash from cache key; rely on TTL only.
> Target: >40% cache hit rate on realtime path measured from `_diagnostics.grounding.prefetch.cache_hit`."

### 4. Add an observable success criterion

None of the existing documents define a measurable verification step for the cache fix.
`cache.md`'s "Definition of Done" checks that the field exists in the response, not
that it is ever `true`. A correct criterion is:

> "Over a 5-minute recorded session at normal conversational pace, `cache_hit: true`
> appears in at least 40% of realtime `_diagnostics.grounding.prefetch` entries."

Without this, any implementation — correct or not — can be declared done.

---

## Summary

The fix recurs because a single LLM analysis pass made a subtle reasoning error
(conflating semantic similarity with hash equality), encoded that error into documents
that suppress re-investigation, and those documents are now part of the canonical
context read by every subsequent agent. The error is locally coherent, passes casual
testing, and is protected by an explicit instruction not to re-derive. Fixing the code
without fixing the documents will result in the same fix being proposed again within
one or two sessions.
